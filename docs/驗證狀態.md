## 5. 封存與修正版：設計已建立，強制斷電未驗證

目前建立的設計：

1. `archive/.import.lock` 排他鎖，僅允許單一離線匯入者，異常殘留阻擋後續匯入。
2. 來源先複製成 `archive/.<token>.pending`，驗證 SHA。
3. SQLite backup API 建立交易前完整備份 `archive/.<token>.db.pending`。
4. `BEGIN IMMEDIATE` 整日交易替換，commit 後 `os.rename` 正式封存。
5. 改名失敗用 SQLite backup API 回復提交前狀態。

跨檔案系統／SQLite **不具分散式原子性**，強制中斷或斷電尚未驗證。檢視設計不能證明斷電可安全回復。

殘留處理：先停止所有程式、備份整個 `data`，檢查 `import_batch` 成功批次與封存 SHA。未正式封存時以匹配 `.db.pending` 經 backup API 回復；正式封存對應成功批次且 SHA 正確或回復確認後才清理對應暫存與鎖。**不得直接刪備份或解除鎖繼續匯入。** 不確定狀態時保留阻擋；人工回復程序也需要實測紀錄。

追蹤情境：首次匯入、相同檔重匯、有效 v2、衝突版本、無效 v2、被占用輸出、模式隔離、重建再匯入。已回報整體測試與完整 CLI 結果；未提供個別證據的情境不據此逐項宣稱通過。

agent Linux 實測最新 54 項通過（9.23 秒），包含改名失敗補償、補償也失敗的殘留阻擋、整週空窗與識別碼文字型別。再次 run 同檔跳過不增量，全部封存 SHA／批次相符，資料庫完整性／外鍵通過。未提供逐項名稱的其他情境不擅自逐項勾選；強制斷電與人工 PowerShell 回復程序仍待實際驗收。
